Research

Learning from what already works

Before drawing anything, I collected screens from other event products and wrote down what each one did well.

Venga

Simple event creation with dress code and extra info. One place for invites, RSVPs and photo sharing. Clubs for recurring events.

Luma

A minimal discover page with categories. A map for browsing events. A very good event-name typeface.

A Dribbble app

Add events to favourites, category tags, a quiet layout with warm colour balanced by black and white.

Creation flows

Start by choosing a category, then add detail. A clear choice of who can see the event.

Profile pages

A clear structure. See who is attending, and which events your friends joined. Interests and preferred places are worth having.

What we took

Minimal layout, categories first, warm accent colour, a serif for event names, favourites as a heart.

Define

What each page needs to do

We wrote the content for every page before designing it, so developers and designers worked from the same list.

Browse

Search bar, filters for location, dates, category and creator. Each event shows image, host, date, approximate place, category, RSVP, how many are going and which friends.

Event details

Everything on the card plus description, min and max participants, who may join, public or private, and host contact. Hosts get an edit button.

Profile

Edit info, saved events, past events, upcoming events and the events I host. A calendar view of the same events.

Sign up and log in

Name, email, gender, age, location and password to sign up. Email and password to log in.

Flow decisions we made along the way

  • Confirm after sign up and after creating an event.After creating an event, take the person straight to that event’s page.
  • No signing up for an event without being logged in.A page reminds the user to log in first, so the action never half-completes.
  • Account pages grouped under the profile.Edit info, delete account, saved events, hosted events and past events all live there.
  • A trade-off we discussed:Requiring an account before browsing is easiest to build but less friendly. We weighed it against a landing page that offers sign up or log in.

Reflection

What I took away, and what’s next

Write the page first

Listing what each page must contain made hand-off to developers much easier.

Designing flows, not just screens

Rules such as “no RSVP without logging in” prevented dead ends before they were built.

Design in code is different

Building the calendar myself showed how many small states a single screen hides.

Known gaps

  • The mobile layout needs work: filter chips overlap, search fields clip at the edge and calendar cells are very narrow.
  • We did not test with users, so none of the design choices are validated yet.
  • Designed but not built: the map, sharing by link and showing friends attending.
